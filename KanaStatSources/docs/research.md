# Sources and limits (API 101051)

Native source: [ESO UI repository](https://github.com/esoui/esoui), API documentation `ESOUIDocumentation.txt` (101051), and `esoui/ingame/stats/keyboard/zo_statentry_keyboard.lua`.

`GetPlayerStat(stat, STAT_BONUS_OPTION_APPLY_BONUS)` is the authoritative rating/integer. `DONT_APPLY_BONUS` does not generically prove a pure base value: resources and recovery can return their full total. The critical-only exception on API 101051 is verified by the controlled naked/no-critical-CP dump #4 and equipped dumps #2/#3 below. Never infer a base from the unexplained remainder.

[ZOS Update 29 notes](https://forums.elderscrollsonline.com/en/discussion/564242/pc-mac-patch-notes-v6-3-5-flames-of-ambition-dlc-update-29) establish base health 16000, magicka/stamina 12000, weapon/spell damage 1000. This rule is limited to API 101051, level 50, CP160+, and explicitly absent battle leveling. Other contexts retain the residual. In that same supported context, verified recovery bases are health 309, magicka/stamina 514, and critical resistance 1320. These follow [UESP author formulas after Update 29](https://github.com/uesp/uesp-esochardata/blob/0e58d0871bd63b994d56c6572d400e500b2e326a/editBuild.class.php#L2328), unchanged in the [Update 32 formulas](https://github.com/uesp/uesp-esochardata/blob/bbe4939b259acfcf9b7dd05e14f7da4ba7c4a8d9/editBuild.class.php#L2437), and independently reproduce the three API 101051 recovery totals in dump #3. Other levels are not extrapolated from these historical formulas. [ZOS Update 26](https://forums.elderscrollsonline.com/en/discussion/528633/pc-mac-patch-notes-v6-0-5-greymoor-update-26/p1) introduced base critical resistance at level 10; this addon only assigns its numeric rating in the supported level-50 context.

[ZOS v1.6.5 notes](https://forums.elderscrollsonline.com/en/discussion/154426/patch-notes-v1-6-5) describe base Critical Hit chance as 10%. The current native baseline is not reconstructed from that nominal percentage. On API 101051, each critical stat uses its own finite nonnegative integer `withoutBonus` captured by `GetPlayerStat(stat, STAT_BONUS_OPTION_DONT_APPLY_BONUS)` as a `flat` rating contribution. Missing or invalid values leave a diagnostic and the residual; the native rating remains explainable when percentage calibration is unavailable. Recovery/resources retain their independently verified bases.

`GetAttributeDerivedStatPerPointValue(attribute, stat)` supplies the native current delta used by `ZO_AttributeSpinner_Shared` for pending stat bonuses. Committed points use this raw delta with operation `flat`, so resource percentages include attributes. The latest native health per-point delta is 122 despite an active 5% Juggernaut: it is not pre-multiplied. UESP resource formulas likewise add attributes before applying resource percentages. Pending points are separate from current totals.

`GetItemLinkArmorRating(link, true)` includes condition and local traits; `GetItemLinkWeaponPower(link)` is the item's power. Main-hand power is attributed directly. Version 1.0.11 also attributes the offhand's baseline power on a verified active normal dual-wield bar, as described below. Item-specific enchant descriptions are already adjusted for Infused. Charged glyphs require an active effect. Trait IDs determine the trait's meaning; unrecognized traits do not contribute guessed values.

`GetItemLinkSetInfo(link, true)` returns normal and perfected active equipped counts. Normal thresholds use their sum; perfected thresholds use only perfected count. `GetItemSetUnperfectedSetId` identifies the family. Family, threshold, perfected flag and description deduplicate shared bonuses across links. Conditional proc descriptions remain candidates even at the required item count.

Version 1.0.13 uses the user's explicitly accepted working hypothesis for flat set weapon/spell damage: floor the weighted mean of each active item's `GetItemLinkSetBonusInfo(link, false, index)` amount, with two-handed weapons weighted twice and other items once. Raw per-item descriptions are cached with equipment; the same family/threshold/perfected status and description structure identify matching bonuses. Resource and other stat bonuses keep the equipped descriptions. Both original and averaged amounts, item values and weights remain in the dump. See [controlled measurements, competing hypotheses and accepted scope](2026-10-06-mixed-set-damage.md); acceptance of the hypothesis is not independent proof of a universal engine formula.

Descriptions support complete RU/EN stat clauses. The parser stops at a conditional/unknown tail, retaining recognized permanent prefixes. It never treats item quantities, proc probability or duration as stat amounts. Raw text, IDs and parsing diagnostics are preserved in dumps.

Version 1.0.14 recognizes the native abbreviated RU critical names (`крит. рейтинг оружия` / `крит. рейтинг заклинаний`). An effect's exact rating and following equivalent rounded chance describe one contribution; only the rating is attributed. In dump #14, active Major Savagery (61667, buff type 4) reports 2629 rating followed by 12%; this exactly equals the previous unknown remainder in both critical stats. [ZOS Update 51 notes](https://forums.elderscrollsonline.com/en-gb/discussion/697154/pts-patch-notes-v12-1-0) establish that Savagery now affects both weapon and spell critical. On API 101051, this stat scope is applied by native `BUFF_TYPE_MAJOR_SAVAGERY`, independent of the granting ability/item, with the captured type 4 retained for replay of old dumps lacking the enum. Generic parsed clauses are copied before applying the buff scope, so cached weapon-only clauses for other effects are preserved. Amounts remain native; neither 2629 nor 12% is hardcoded as a contribution.

Critical conversion is calibrated from `GetCriticalStrikeChance(0/1/100/1000/current/current+1000)` on the running client. It validates slope, intercept and saturation before attributing percentage sources. No universal coefficient is hardcoded. The visible footer shows only the native total chance; rating, calibration and formula helper remain diagnostic data. If calibration is unavailable, source effects show unavailable rather than ratings under a percentage-only UI.

Version 1.0.7 formats every critical source and total with `zo_strformat(SI_STAT_VALUE_PERCENT, chance)`, exactly as [ZO_StatEntry_Keyboard:GetDisplayValue](https://github.com/esoui/esoui/blob/live/esoui/ingame/stats/keyboard/zo_statentry_keyboard.lua#L41). The [native zo_strformat implementation](https://github.com/esoui/esoui/blob/live/esoui/libraries/globals/localization.lua#L5) defaults to one fractional digit for noninteger numeric arguments (lines 18, 30-38). Thus the captured 9.9534492493% appears as 10.0% in the native stat list and both addon cells; the former two-digit source display was 9.95%. The offline/unavailable-formatter fallback likewise uses one decimal. No native rating or conversion coefficient is changed to force a nominal exact 10%.

Critical cells use raw source ratings, avoiding a second rounding from apportioned integer row values. If a nonzero source would format as +/-0.0%, fractional precision increases until the magnitude reaches a decimal digit; a finite tiny-value fallback uses scientific notation after 15 fractional digits. The preformatted ASCII decimal string goes through the native stat formatter; the total retains its numeric format. Version 1.0.8 incorrectly prelocalized the string to a Russian comma; its offline mock failed to enforce the native input contract. This is corrected in 1.0.9, together with the incorrectly inferred Precise rating below. No contribution or residual is discarded by the renderer.

[Native champion data manager](https://github.com/esoui/esoui/blob/live/esoui/ingame/champion/championdatamanager.lua) initializes pending points to saved points. Therefore description/current-bonus calls receive the **saved total**, not zero or a delta. `CanChampionSkillTypeBeSlotted` handles both native slottable types. Active slots come from the committed champion bar. `GetChampionSkillJumpPoints` is captured; no stage is estimated from prose. Current bonus text alone supplies numeric contributions; a per-stage description is never used as a total.

Skills use purchased ability IDs at committed ranks and `GetSkillLineDynamicInfo`'s `isActive` result. Only complete unconditional passive clauses are generic rules. Conditional weapon, armor-count, slotted-skill and subclass interactions require an ID rule with an activation predicate; unsupported interactions remain candidates. Inactive skill lines and unpurchased abilities cannot contribute.

Effects are collected from the player, including foreign casts. Expiry is in seconds while game time is in milliseconds. `endTime=0` is permanent. `GetAbilityBuffType(id, "player")` identifies native named buff families, deduplicating identical Major/Minor buffs across ability IDs. Amounts and affected stats come from current descriptions, accommodating API 101051's merged buffs. Unknown stack rules are not multiplied by stack count.

Mundus membership comes from `GetUnitActiveMundusStoneBuffIndices`, independent of localized names. Values use native `GetAbilityDerivedStatAndEffectByIndex`, as exposed for Mundus stats, with no further Divines multiplication. Food classification uses the observed effect-ID mapping maintained by [LibCombat's author](https://github.com/solinur/LibCombat); unidentified food still appears as a generic effect if its current flat clause is recognized.

The additive percentage group applies to recognized **raw flat** resource/damage sources with a verified base. Raw committed attribute contributions are included; already effective native Mundus contributions are excluded. Supported recovery percentages now apply to the verified recovery base plus recognized raw flat sources. This is deliberately a partial attribution: percentage effects on unknown flats, special multiplicative sets, unsupported weapon passives, conditional armor/skill bonuses, curse and environment scaling remain in `Unknown`. No inverse calculation assigns the remainder to a fabricated source. Each percentage row stores its exact numeric base in the dump.

## Offhand damage and additive armor percentages, version 1.0.11

The [UESP author's item-power calculation](https://github.com/uesp/uesp-esochardata/blob/master/resources/esoEditBuild.js#L2327) applies `floor(weaponPower * 0.178)` to the offhand, then adds that integer to both raw weapon and spell damage. This is an item-power rule, not a lookup for a particular dagger, set, quality or level. The native item's power already includes its local weapon trait; it is not modified a second time. Only the active PRIMARY/BACKUP bar with matching native weapon-pair metadata and two one-handed axes, maces, swords or daggers enables the rule. Shields, missing types and nonstandard/ambiguous weapon contexts stay diagnostic. Additional weapon passives still require their own verified rules.

Controlled API 101051 dumps #9 and #10 independently match this calculation. The 1132-power offhand supplies `floor(1132 * 0.178) = 201`. The flat subtotal is `1000 + 1132 + 201 + 124 + 150 = 2607`. Major Brutality adds 20%; Agility's native current bonus changes from 0% to 2% with the medium shoulder. These percentages share the flat base: `round(2607 * 1.20) = 3128`, then `round(2607 * 1.22) = 3181`. The shoulder's raw contribution is 52.14; rounding the combined subtotal explains the native +53 delta. It is not 2% of the already buffed 3128.

Previously the missing offhand also excluded its portion of the percentage rows. The addon explained `round(2406 * 1.20) = 2887` and `round(2406 * 1.22) = 2935`, leaving 241 and 246 respectively. The new source makes both integer residuals zero without changing rounding, native totals or unknown handling. Raw rounding differences remain in dumps. Replay also removes the damage residuals in #7 (3128) and #8 (4488), including the latter's 14% Agility. Synthetic tests cover arbitrary one-handed weapon types and powers, backup/inactive bars, rejection of shields/incomplete context, and retention of an unrelated unknown +7; they do not claim live validation of every possible weapon/passive combination.

The two-column table displays the numeric contribution and percentage; the exact multiplication base, slot/rank/CP details and source evidence remain in dumps. Known contributions use compensated summation and largest-remainder rounding: round their raw subtotal once, floor individual values, then allocate the missing units by descending fractional parts, with stable source-order ties. For 3148 + 14% + 20%, the raw total is 4218.32 and displayed rows total 4218, avoiding the old independently-rounded 4219. A genuine integer excess still produces Unknown -1. Compensated summation also preserves the exact half-unit total 3007.5 in the tank fixture; no rounding epsilon or residual-dependent tolerance is used. Raw amounts, `rawExplained` and `rawUnknown` remain in the dump. Rounded-zero rows are omitted from the display; captured sources and contributions remain available.

Generic passive contributions sharing an ability ID and stat with an emitted active-effect contribution defer to the active effect. Distinct ability IDs and unrelated stat clauses are preserved. Native nilable results remain nilable; required collection counts and numeric results are validated before traversal. Category collectors are isolated so malformed metadata does not abort the character snapshot.

The native [keyboard stat tooltip](https://github.com/esoui/esoui/blob/live/esoui/ingame/stats/keyboard/zo_statentry_keyboard.lua) supplies the original localized title, description and display value. The addon prehooks only its 15 recognized main stats. Text and sources share one private ZO_BaseTooltip inside TooltipTopLevel, matching [native templates](https://github.com/esoui/esoui/blob/live/esoui/ingame/tooltips/tooltips.xml). The shared InformationTooltip is never modified. [Native ClearTooltip](https://github.com/esoui/esoui/blob/live/esoui/ingame/tooltips/tooltips.lua) preserves content during fade; the view releases controls on hiding/clearing, not on mouse exit.

Width uses source-cell measurements only, floored at the untouched native default maxX (350 UI units), bounded by the screen. Header/description and attribute preview wrap inside it. Height and width use hidden native Label:GetTextDimensions probes without reading previous tooltip dimensions or scaling the block. A refresh with unchanged width preserves height/scroll; changed source width recalculates height to accommodate title wrapping. Visible labels are assigned final dimensions only, and unchanged title/description text is not rewritten. All text uses ZoFontHeader, as in native character stat labels.

API 101051 documents GetTextDimensions as returning UI units and GetStringWidth as returning a scaled native width. Natural width uses a zero-width probe; wrapped height uses the target width and a generous height, avoiding a constrained visible label's metrics. [Native ZO_TooltipSection:AddCustomLabelInternal](https://github.com/esoui/esoui/blob/live/esoui/libraries/zo_tooltip/tooltip.lua) likewise sets width and reads GetTextDimensions. The scaled nature of GetStringWidth is also confirmed by [ZOS staff](https://www.esoui.com/forums/showthread.php?t=1831), post12; the addon does not use it as an unscaled dimension setter input.

Equipment/set icons come from GetItemLinkIcon; passive/effect icons come from native skill/buff metadata. CP uses the discipline ID/type and the same green/blue/red point-pool icons as [ZO_ChampionDisciplineData:GetPointPoolIcon](https://github.com/esoui/esoui/blob/live/esoui/ingame/champion/championdatamanager.lua). The discipline index and star ability ID do not determine the colour.

Base rows use the native character-menu icon. Attribute rows use `/esoui/art/characterwindow/Gamepad/gp_characterSheet_{health,magicka,stamina}Icon.dds`, identical to KanaWardrobe/EffectModel.lua's info-panel metrics.

## Verified passive additions in 1.0.5

ID 185239 (Erudition) is recognized only by its complete native RU/EN unconditional description, including its flavor sentence. The percentage comes from that text; a conditional tail or foreign ID does not qualify. The generic parser still stops at unknown prose.

ID 29397 (Sword and Board) requires a captured native PRIMARY/BACKUP hotbar category consistent with the front/back bar and weapon pair, known active main/offhand slots, a native one-handed axe/hammer/sword/dagger in the main hand and a shield in the offhand. Its full current RU/EN description supplies the damage percentage; purchased and active-line checks remain required. An inactive shield, dual wield, staff, two-handed weapon, werewolf bar or missing metadata cannot activate it.

Dump #4 (addon 1.0.5) removes all equipped items and critical CP and switches to the penetration Mundus. Both critical totals and `DONT_APPLY_BONUS` values are exactly 2181, with native `GetCriticalStrikeChance(2181)=9.9534492493%`. The old rule converted exactly 10% into 2191.2000613031 rating, inventing a -10.2000613031 raw residual (-10 displayed rating, approximately -0.05%). Version 1.0.6 uses the captured native critical baseline instead. Replaying unchanged dumps #2/#3 gives 2181 + 1701 Mundus + 160 CP = 4042 exactly; dump #4 gives 2181 alone with no residual. The separate -1 rating residual in dump #1 is explained and fixed by the Precise measurement below. The internal engine formula that creates 2181 is not established. See [controlled comparison](2026-10-06-native-critical-base.md).

## Precise integer rating and percentage localization in 1.0.9

Controlled dump #6 has only one purple CP160 Precise lightning staff. Both critical stats are 3539, versus 2181 in naked dump #4: the measured trait delta is exactly 1358. The captured text says 6.2%, while reversing the API display conversion gives 1358.5440380079. Rounding that estimate to 1359 invented an extra rating point and a negative unknown. A rounded text percentage is not an exact numeric rating; neither a universal floor rule nor an engine quantization formula is established by this observation.

Version 1.0.9 emitted the measured integer 1358 only for the purple CP160 lightning staff. This narrow lookup was removed in 1.0.10: it caused the Precise contributions of two daggers in dump #7 to become unknown. The independent full-build dump #1 reconciles both crits: 2181 + 1358 + 634 + 634 + 1897 + 160 = 6864. The original sanitized fixture's omitted item metadata was restored from its original dump; no expected outcomes were injected into source input.

The [native localization implementation](https://github.com/esoui/esoui/blob/live/esoui/libraries/globals/localization.lua#L129) explicitly requires English numeric separators before grammar formatting. Version 1.0.8 violated this contract for small Russian percentages by passing a prelocalized comma string. Version 1.0.9 keeps ASCII decimal strings until the native formatter; Russian substitution is used only in the offline fallback. Formatter regressions assert the input contract rather than treating already-localized strings as accepted. The native client grammar itself is not available to the offline harness.

## General Precise conversion in 1.0.10

Dump #7 contains two identical purple CP160 daggers, each with a native 3.1% Precise description, and Precision CP providing a separately captured 160 rating. No critical-chance passive or effect adds another contribution. Both critical totals are 3699: 3699 - 2181 baseline - 160 CP = 1358 from the pair, or 679 each. Compared with dump #6, both 6.2% and 3.1% agree with per-item integer conversion: floor(chancePercent * calibratedPointsPerPercent). This source quantization occurs before general subtotal rounding; it does not absorb a remainder or change the native total.

The generic `criticalChanceInteger` operation uses the live calibration separately for each critical stat. Equipment emits the percentage from its native Precise ID/description, with no item ID/name, weapon-type, quality, level, API-version or CP lookup. Its full description already supplies the one/two-handed magnitude, as in the [UESP author's item-trait parser](https://github.com/uesp/uesp-esochardata/blob/master/resources/esoEditBuild.js#L2457); that parser does not establish the engine's integer rounding. Missing or nonlinear critical conversion remains diagnostic/unknown; ordinary fractional critical-chance sources retain their existing operation. Other item traits retain their existing rules.

Live numeric evidence for this quantization comes from the supplied dumps; synthetic tests prove generic scope and use of the current curve, not native results for every possible quality/level/set interaction. Actual replay of dumps #1–#7 gives zero integer/raw critical residuals in all fourteen tables. Dump #7 has baseline 2181, two distinct 679 item rows with icons, and a 160 CP row, displayed as 10.0%, 3.1%, 3.1%, 0.7%, total 16.9%. CP removal changes only the CP contribution. An extra unidentified +7 remains unknown. Tests also cover a different native coefficient, a changed item percentage, arbitrary item metadata, and inactive-bar rejection.

Native PRIMARY/BACKUP enums are now captured explicitly. A category-change event invalidates current context without dropping equipment/build caches. Legacy 1.0.4 snapshots lack those enums, so offline replay supplies the existing collector test API enum metadata; the serialized fixture itself is unchanged. A legacy snapshot with no supplied enum metadata conservatively retains the 73 damage residual. Runtime code never hardcodes or infers these enums.
