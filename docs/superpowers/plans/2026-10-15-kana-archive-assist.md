# KanaArchiveAssist Implementation Plan

> Исторический план первой реализации. Модель и условия показа заменены по последнему запросу пользователя; текущий план: [sparse learning](2026-10-15-kana-archive-assist-sparse-learning.md). Старые проверки поддержки и ансамбля ниже больше не являются действующими требованиями.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** отдельный аддон, который учится на подтверждённых выборах строф и видений, учитывает текущие видения и показывает обоснованные личные предпочтения семью плоскими метками.

**Architecture:** игровой адаптер передаёт неизменяемые снимки в автомат регистрации выборов; история и настройки разделены по профилям. Чистое математическое ядро обучает 16 регуляризованных контекстных моделей, проверяет поддержку запроса данными и преобразует результат в метки. Контроллер публикует только целиком рассчитанные результаты; UI использует собственные контролы рядом со штатным селектором.

**Tech Stack:** совместимый с ESO Lua, штатные SavedVariables, keyboard UI и центр экранных уведомлений; локальные Lua-тесты. Python с NumPy нужен только для независимого численного эталона при разработке, не устанавливается пользователю и не вызывается аддоном.

**Spec:** [2026-10-15-kana-archive-assist-design.md](../specs/2026-10-15-kana-archive-assist-design.md). Исполнитель читает и спецификацию, и план. Статус: реализовано по команде пользователя «теперь реализовывай»; фактическое выполнение и отклонения записаны в конце документа. Клиентская приёмка ESO ещё не выполнена.

## Global Constraints

- Имя нового аддона — `KanaArchiveAssist`; единственная команда — `/kaa`, без подкоманд.
- Первая версия — только клавиатура и мышь. Gamepad не подключает ни рекомендации, ни обучение.
- Эталон оформления — [конкретная картинка, приложенная пользователем](../specs/assets/kana-archive-assist-approved-flat-markers.png). Плоские широкие шевроны и линия; рельеф, объём, цветное свечение и замена эталона интерактивным макетом исключены.
- Значения меток: `-3, -2, -1, 0, +1, +2, +3`; `nil` означает отсутствие значка и области наведения. Жёлтый не обозначает нехватку данных.
- Два равных фаворита — зелёный/зелёный/красный; один фаворит — зелёный/красный/красный; строгая тройка — зелёный/жёлтый/красный; все близки — три жёлтых.
- Тултип показывает только реальные числа для совпадающих вариантов и видений; нет таких наблюдений — нет тултипа, а метка не принимает мышь. Пересказ цвета/силы шевронов исключён.
- Неизученный текущий контекст скрывает метки. Запасного общего рейтинга, принудительного исследования вариантов и советов без поддержки данными нет.
- Одно предложение и один подтверждённый победитель — одно наблюдение. Не выводить порядок между проигравшими и не удваивать статистическую уверенность разбиением тройки.
- Полная история сохраняется; рабочее окно — 2000 выборов каждого типа в профиле. Строфы и видения обучаются отдельно.
- Профили общие для аккаунта на одном сервере; активный профиль и пауза — для персонажа. Первый профиль `default` имеет постоянный ID и сохраняется после переименования.
- Пауза действует до явного включения обучения; контекст и рекомендации продолжают обновляться.
- Профиль и режим — центральное уведомление на 5 секунд, без звука. Нехватка данных — одно сообщение в чат на актуальное предложение/профиль.
- Сохраняются штатные заголовок, варианты, названия, выбор, подсказки, переброс, валюта, масштабирование и соседние достижения с прокруткой. ArchiveHelper, Reminderz и KanaArchiveAchievements не редактируются и не становятся обязательными зависимостями.
- До первого push весь аддон, дизайн, этот план, тесты и документация остаются в одном изменяемом jj-коммите `llosqrwymqsvszuwtrmntvkpvomrqklu`. После законченного этапа проверять `jj status` / `jj diff` и добавлять только его пути через `jj squash --into`; отдельные коммиты этапов и push не делать.

## Review Focus

1. `OnHiding` раньше серверного результата: скрытие UI не теряет корректное ожидающее подтверждение и не создаёт голос повторно — задача 2.
2. Перезагрузка внутри рана и неоднозначное восстановление: не увеличивают число независимых ранов и не переигрывают старый выбор — задачи 1–2.
3. Новый соперник или исчезновение всегда присутствовавшего видения: одинаковые нулевые коэффициенты ансамбля не превращаются в уверенность — задача 4.
4. Смена профиля/предложения во время расчёта: старый результат не появляется под новым профилем, а ожидающий выбор остаётся у профиля подтверждения — задачи 2 и 8.
5. Большая иконка, яркий нативный эффект и уменьшенное окно: метка не отнимает наведение у перка, последний профиль и нижние карточки остаются доступны — задачи 7–9.

## Порядок и границы работ

Основной порядок: **хранилище → регистрация выбора → обучение → проверка контекста → градации → проверка качества → метки и тултип → окно и объединение → клиентская приёмка**. Математические задачи 3–6 можно выполнять независимо от ожидания игровых наблюдений задачи 2. Вывод рекомендаций включается только после прохождения численной проверки; сбор достоверной истории не зависит от готовности модели.

Расположение ещё не подтверждено в игре. Стартовое предложение из спецификации: область 32×32 за правым краем фактического `Icon`, зазор 6, центры по Y совпадают. Форма берётся из выбранной картинки. Этот технический якорь не объявляется визуально одобренным по макету: приёмка задачи 9 должна проверить его на настоящих иконках и свечении. Высокий ряд и сдвиг заголовка не возвращаются автоматически.

### Общие записи и интерфейсы

- `Context = {visions={{abilityId, stacks}, ...}, arc?, cycle?, stage?}`: видения отсортированы по ID, положительные целые стаки. Только `visions` участвует в модели v1.
- `Offer = {offerId, runId, buffType, options={abilityId, ...}, context, timestamp}`: 2–3 уникальных положительных ID; порядок показа хранится отдельно от сортировки признаков.
- `Attempt = {offer, selectedId, profileId, learningEnabled, previousStackCount}`: глубокая копия при подтверждении; поздние изменения не меняют запись.
- `Observation = {schemaVersion, observationId, runId, profileId, buffType, options, selectedId, context, timestamp}`: только подтверждённый обучающий выбор.
- `Dataset = {profileId, buffType, rows, revision, featureKeys, runWeights}`: окно одного профиля/типа; `row` хранит целое предложение, вес давности и индекс обучающего рана.
- `ModelSnapshot = {version, profileId, buffType, historyRevision, members, configVersion}`: неизменяемые параметры всех 16 сошедшихся моделей.
- `ChoiceStats = {total, runs, countsById}`: невзвешенные реальные количества из Dataset при точном совпадении типа, вариантов и всех видений со стаками. Нет совпадений → `nil`.
- `Prediction = {modelVersion, byId, support, reason}`; `byId[id] = {grade?, role?, comparisonIds}`. Для неизвестной оценки `grade` отсутствует, а не равен нулю.
- Задания обучения/поддержки: `job:Step(deadlineMs) -> done, result, reason`; время передаётся через `clockMs()`. `Controller` вызывает их между кадрами и проверяет актуальность результата.

## Задача 3: разреженная контекстная модель и ансамбль

**Files:** создать `Features.lua`, `ChoiceModel.lua`, `tests/test_model.lua`, `tests/reference.py`, `tests/fixtures/numerical.lua`; дополнить `Config.lua`.

**Interfaces:** `Features.BuildRows(offer, featureIndex) -> rows, updatedIndex`, `Features.Difference(rows, i, j) -> sparseVector`; индекс сохраняет неизвестные координаты запроса. `ChoiceModel.LossGradient(theta, dataset, memberRunWeights) -> loss, gradient`; `ChoiceModel.NewFitJob(dataset, previousSnapshot, seed, clockMs) -> job`; `ChoiceModel.Predict(snapshot, offer) -> memberUtilities, memberProbabilities`.

- [ ] В `test_model` проверить категориальную потерю одной тройки против ручного softmax; перестановка вариантов сохраняет вероятности по ID. Численная производная совпадает с градиентом с относительной ошибкой ≤ `1e-5`; оценки ±1000 дают конечные вероятности и потерю.
- [ ] Реализовать точную формулу спецификации: `a_i + Σ b_i,v·f(stacks) + Σ c_i,j`, четыре признака стаков, устойчивые softmax/log-sum-exp. Ключи признаков сортируются детерминированно. Штраф `0.5*(0.25*||a||² + 2*||b||² + 1*||c||²)` добавляется к сумме потерь, без скрытого деления на размер истории.
- [ ] Реализовать L-BFGS с памятью 8, нулевым либо тёплым стартом, Armijo `c1=1e-4`, начальным шагом 1 и половинным уменьшением до 24 попыток. Неположительная кривизна пары сбрасывает память и использует отрицательный градиент. Критерий сходимости: `||grad||∞ <= 1e-6 * max(1, ||grad_initial||∞)`; максимум 500 итераций на участника. Лимит/NaN/неуспешный поиск шага не публикуют несошедшуюся модель. Это стартовые параметры `modelConfigVersion=2`, проверяемые независимым эталоном.
- [ ] Делить вычисление потери, градиента и векторные операции на возобновляемые части с проверкой переданного deadline; не только между полными итерациями оптимизатора. 16 участников обслуживать последовательно с сохранением состояния, без 16 параллельных полных пересчётов.
- [ ] Зафиксировать PRNG для разработки/рановых весов: Park–Miller с арифметикой, безопасной для double Lua; никаких `math.randomseed` и изменения глобального генератора игры. Получать `Poisson(1)` обратной CDF из воспроизводимого равномерного значения по `(savedSeed, memberIndex, runId)`. Один вес на весь ран, учебный вес = давность × этот вес. Версионировать генератор.
- [ ] Независимый `tests/reference.py` использует NumPy, плотные признаки и Newton с плотным решением Hessian; он не вызывает Lua-потерю/L-BFGS.
