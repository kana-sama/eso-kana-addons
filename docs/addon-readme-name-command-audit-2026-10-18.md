## Требования пользователя

1. У **каждого** аддона должен быть собственный `README.md` **на русском**. Для самостоятельного аддона описывать **одной короткой ёмкой фразой** главную пользу игроку: что появляется или меняется и где. Пример пользователя: для панели пробития важно, что она появляется **под полосой здоровья цели**; возможность менять параметры панели в таком README не нужна. Первый длинный README пользователь отклонил: «слишком много слов, нужно короткое и емкое. Что-то типа „Постепенное показывание текста диалогов“, только получше придумай». **Исключение для надстроек:** отдельными короткими пунктами перечислять заметные игроку правки оригинала и важные возможности настроек. Пример пользователя: у Kana AetherChat Patch важно указать, что он позволяет скрывать плавающий квадратик AetherChat. Списки предпочтительнее перечисления через запятую. Технические детали и тесты в пользовательский README не переносить.
2. Проходить аддоны по одному, но после пилота задавать вопросы **пакетами через встроенный UI вопросов**, предлагая варианты ответов, чтобы не отвлекать пользователя слишком часто. Первый аддон — **тест флоу**; прежде чем масштабировать пакеты, проверить, что формат вопросов и ответов удобен.
3. Для каждого аддона сначала изучить код и составить русский пользовательский README, сохранить его в папке аддона и **показать пользователю**. На основе этого текста пользователь выбирает имя. Предложить **ровно пять** осмысленных названий с `Kana`, отметить рекомендуемое, дать возможность назвать свой вариант. Не закреплять имя до ответа.
4. После выбора оформить видимое название с красным `Kana`, остальными словами белым и пробелами. Если это **надстройка** другого аддона, название оригинала — **синим и в его точном написании**. Пример пользователя: `Kana AetherChat: focus fix`, где `AetherChat` синим и слитно. **Форк не считается надстройкой**: исходный аддон в название не добавлять без выбора пользователя. Технические идентификаторы остаются PascalCase; при изменении не терять SavedVariables.
5. Для каждого аддона отдельно выдать **все добавленные им команды** с назначением и спросить, какие оставить, а какие заменить контекстным меню или другим уместным элементом интерфейса **и где именно**. Предлагать варианты ответа. Пример пользователя: ускорение диалога в `KanaSlowDialogue` лучше размещать в контекстном меню диалога, а не отдельной командой. Не изменять команды до ответа.
6. Ответы, выбранные имена, решения по командам и готовность README фиксировать в этом журнале по мере работы. Не пушить без прямого запроса. Изменения каждого аддона отделять от общих правил и чужой параллельной работы.
7. **Все изменения интерфейса в этой задаче** собирать в единый **короткий** игровой чек-лист `docs/addon-ui-validation-checklist-2026-10-18.md`, чтобы пользователь в конце проверил, что всё ещё работает. Не расписывать сценарии: для пилота достаточно одного пункта «Kana Dialogue: slow text — проверить контекстное меню в диалогах». Подробные условия проверять локальными тестами.
8. Пользователь добавил правило для **всех надстроек**: каждая его собственная правка должна отключаться отдельным чекбоксом в настройках **надстройки**, а не исходного аддона. Сохранять текущее поведение по умолчанию; при технической необходимости помечать переключатель как требующий `/reloadui`. Форки не подпадают под это правило автоматически. Сначала определить действительные надстройки по интеграции с исходными аддонами, затем инвентаризировать их отдельные правки и дать каждой переключатель.
9. При переименовании сохранять прежний технический ID и имена, версии, области, namespace и ключи SavedVariables, чтобы настройки всех пользователей читались из прежних файлов. Если схема всё же должна измениться, нужна миграция и тест старых данных до выпуска. Проверять не только пользовательские файлы, но и точный вызов `ZO_SavedVars`.

### Отправленный пилотный пакет вопросов

README: «В диалоговом окне ESO текст реплик появляется постепенно, но его можно сразу раскрыть вместе с вариантами ответа, не выбирая ответ случайно. Для отдельного собеседника или доски объявлений можно запомнить мгновенный показ следующих реплик. Служебные разговоры с торговцами, банкирами и другими подобными персонажами не заставляют ждать окончания анимации текста. Работает в клавиатурном интерфейсе игры». Пользователь должен подтвердить или поправить.

Пять предложенных имён: `Kana SlowDialogs: Dialogue Pace` (рекомендовано), `Kana SlowDialogs: Instant Text`, `Kana SlowDialogs: Reveal Replies`, `Kana SlowDialogs: Speaker Pace`, `Kana SlowDialogs: Dialogue Reveal`. `Kana` — красный, `SlowDialogs` — синий, остальное — белое.

Найдена одна команда `/kslow`: переключает мгновенное появление текста для текущего собеседника или доски объявлений. Предложены варианты: удалить команду и добавить переключатель в контекстное меню имени собеседника/доски (рекомендовано); оставить команду; удалить команду и добавить кнопку в окно диалога. Уже существующий щелчок по имени раскрывает только текущую реплику.
