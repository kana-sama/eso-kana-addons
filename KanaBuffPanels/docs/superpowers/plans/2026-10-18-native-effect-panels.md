# Kana Buff Panels Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Распределять существующие штатные иконки эффектов персонажа по пользовательским панелям и скрывать выбранные эффекты, сохраняя работу системы ESO.

**Architecture:** Штатный контейнер персонажа остаётся единственным владельцем сбора эффектов, пулов и обновления таймеров. Небольшой адаптер запоминает порядок выдачи готовых контролов и после штатной перестройки меняет их размещение; панели регистрируются в HUD_MANAGER. Правила и геометрия — простые Lua-модули без собственного трекера и редактора.

**Tech Stack:** ESO API 101051, Lua 5.1, LibAddonMenu-2.0, LibCustomMenu; тесты через Python и `lupa.lua51` (`lupa==2.8`).

**Spec:** [Согласованный дизайн](../specs/2026-10-18-native-effect-panels-design.md).

## Global Constraints

- Отображаемое название: `|cFF0000Kana|r Buff Panels`; техническое имя: `KanaBuffPanels`.
- Только эффекты своего персонажа: `player`. Панель `reticleover` и её настройки не меняются.
- В настройках аддона у панели редактируется только имя; там же создание, удаление и чёрный список.
- Положение, «Ориентация» и «Рост» настраиваются в штатном редакторе HUD. Пустая панель тоже доступна в нём.
- Строка: «Вправо / Влево / От центра»; колонка: «Вниз / Вверх / От центра». Начальное состояние — строка вправо.
- Приоритет: чёрный список → существующее назначение → стандартная панель. Скрытие сохраняет назначение.
- Одна строка или колонка без переноса. Сохраняются штатные иконки, таймеры, стаки, мигание, порядок внутри групп и условия видимости.
- Дополнительная работа при перестройке — O(E + P); нет собственного опроса эффектов, подписок на боевые эффекты или цикла таймеров.
- Положение и параметры раскладки сохраняет HUD_MANAGER; имена, назначения и чёрный список — account-wide `KanaBuffPanelsSV`.
- Не переносить код или настройки KanaEffects. Не менять соседние аддоны и глобальные классы ESO.
- До первого push весь аддон, включая эту спецификацию и план, остаётся одним изменяемым коммитом. Использовать только `jj`; push не разрешён.

## Review Focus

1. Контрол скрытого эффекта персонажа переиспользован для цели: старое правило и обработчик меню не должны сработать на цели. Тест этапа 3 и повтор в этапе 5.
2. Эффект меняется, пока открыто меню: выбранное действие относится к эффекту на момент открытия. Тест этапа 5.
3. Все иконки ушли со стандартной панели, затем вернулись: нет старых размеров, промежутков и якорей на чужих панелях. Тест этапа 3.
4. Чётное/нечётное число иконок, высокий таймер и смена масштаба: опора неподвижна, подписи не перекрываются. Тесты этапов 2 и 4.
5. Панель удалена, переименована или восстановлена до готовности сохранений HUD: назначения и координаты не теряются, удалённое имя не возвращается. Тесты этапов 1, 4 и 6.

## Файлы и договорённости

Все новые файлы ниже находятся в `KanaBuffPanels/`. Простые модули публикуются в одной таблице `KanaBuffPanels`; отдельный API-фасад, шина событий и универсальный renderer не нужны.

| Файл | Ответственность |
| --- | --- |
| `Rules.lua` | Сохранённые панели, назначения, скрытие и идентификаторы эффектов |
| `Layout.lua` | Чистая геометрия одной строки/колонки |
| `Native.lua` | Работа с двумя метапулами персонажа, порядок контролов, стандартная раскладка |
| `Panels.lua` | Контейнеры панелей, HUD_MANAGER, измерение и размещение |
| `Menu.lua` | ПКМ на заимствованной штатной иконке |
| `Settings.lua` | Страница LibAddonMenu, управление именами и скрытыми эффектами |
| `Strings.lua`, `Core.lua`, `KanaBuffPanels.addon` | RU/EN строки, жизненный цикл, манифест |
| `tests/run.py`, `tests/requirements.txt`, `tests/support/eso.lua` | Компактный раннер Lua 5.1 и мок границы ESO |
| `tests/{rules,layout,native,panels,ui,integration}.lua` | По одному набору на этап |
| `README.md`, `docs/validation.md` | Пользовательские инструкции и фактические результаты проверок |

Контракты данных:

- `PanelId` — возрастающее положительное целое, не переиспользуется после удаления. `EffectKey` — `ability:<id>` или `artificial:<id>`; одинаковые имена не объединяются.
- Сохранения: `nextPanelId`, `panels[id] = {name}`, `assignments[key] = panelId`, `hidden[key] = {name}`. Имя скрытого эффекта — подпись на момент скрытия; ID всегда виден в списке. Начальные таблицы пустые.
- `Destination` — числовой PanelId, строка `default` или `hidden`. Неизвестное назначение даёт `default`.
- Значения HUD ENUM: `orientation = 1` (строка), `2` (колонка); `growth = 1` (вперёд), `2` (назад), `3` (от центра). При смене оси число growth сохраняется.
- `Metrics = {width, height, labelHeight, gap}` в единицах UI; gap равен штатным 5. Высота подписи измеряется отдельным скрытым label тем же шрифтом и шириной, без чтения старой выделенной высоты pooled label. Сохранять запас для двух строк штатного Duration; пересчёт при смене штатного оформления, не на каждом тике таймера.
- `IconGroups = {[panelId] = {control, ...}}` содержит те же объекты, что выданы ESO. Группировка сохраняет порядок выдачи сначала buffPool, затем debuffPool; отдельная сортировка не нужна.

## Общая процедура сохранения и финального ревью

Перед каждым сохранением: `jj status`, `jj diff --git`, проверка состава и пробелов. Проверить, что исходный change `klrotwsuzyzw` остаётся изменяемым и не входит в `::remote_bookmarks()`/`immutable()`. Затем `jj squash --into klrotwsuzyzw --use-destination-message KanaBuffPanels` добавляет этап в тот же коммит. Изменение общего README включать отдельным явным путём только на этапе 6. Не включать соседний коммит AGENTS.md и чужую рабочую копию; для первых сохранений папки достаточно одного пути.

К концу работы обновить описание этого change по итоговой реализации, сохранив префикс `KanaBuffPanels:`. Если коммит успел стать опубликованным или immutable, историю не переписывать: использовать новый scoped commit согласно AGENTS.md.

Финальное ревью проверяет границы native ownership, отсутствие новых циклов/сканирований, стабильность якоря, отсутствие побочных изменений target/UI и соответствие спецификации. Его способ зависит от выбранного пользователем режима исполнения; план сам по себе не запускает агентов и реализацию.

## Самопроверка плана

- Требования спецификации распределены по этапам 1–6; все пять Review Focus имеют конкретные проверки.
- Interfaces используют одинаковые имена данных и методов; этапы 3–4 временно стыкуются через тестовый `panels:Render`.
- Добавлены только необходимые контейнеры, правила и настройки; нового сборщика, renderer и таймерного цикла нет.
- Автоматические проверки и клиентская приёмка разделены; начальная разработка сохраняет один коммит.
- Рекомендуемое исполнение: самим агентом последовательно в этом чате, затем одно независимое ревью. Этапы тесно связаны владением общими native-контролами; отдельный новый исполнитель на каждый этап добавит передачу контекста без независимой работы.
