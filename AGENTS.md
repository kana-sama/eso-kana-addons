# Рабочие правила для агентов

## Коммиты и Jujutsu

- Когда фича или фикс готовы и необходимые проверки завершены, коммить результат без отдельного напоминания. Не оставляй готовую работу только в рабочей копии.
- Для нового аддона до его первого push держи один коммит на весь аддон: дизайн, спеку, план, реализацию, тесты и документацию. Этапы первоначальной разработки не считай отдельными фичами; промежуточные коммиты объединяй в этот единственный коммит.
- После первого push аддона каждая последующая фича или правка — отдельный коммит. Не смешивай независимые изменения; при необходимости выделяй файлы конкретной задачи.
- Начинай описание коммита с имени аддона, например `KanaInfoBar: ...`. Для общих изменений репозитория используй префикс `chore: ...`.
- Если после завершения фичи обнаружен фикс к ней, а её коммит ещё не запушен и остаётся изменяемым по правилам `jj` (не `immutable`), добавляй фикс в тот же коммит. Для безопасности предпочитай `jj squash --into <change-id> <пути>` после проверки состава изменений. Для уже опубликованного или неизменяемого коммита создавай отдельный коммит.
- Для просмотра изменений, создания и исправления коммитов и публикации используй `jj`, а не команды `git`. Перед коммитом или squash проверяй `jj status` и `jj diff`.

## Короткие исправления без потери качества

- Если пользователь дал стек с файлом и строкой, начинай с этого участка, вызывающего кода и подходящего тестового стенда. Ищи остальные вхождения проблемного API в затронутом аддоне. Не начинай с обхода всего монорепозитория, всех документов или истории чата.
- Собирай независимые чтения в один вызов инструментов. Повторно читай участок только если изменилось содержимое или появился конкретный вопрос, на который прежнее чтение не ответило. Не перечитывай уже известные правила и принятые решения без причины.
- Для ясного локального бага не открывай новый цикл обсуждения дизайна, выбора вариантов, планирования или делегирования. Сначала исправь уже согласованное поведение. Новый план нужен при изменении требований или архитектуры.
- Воспроизведи именно нарушенное условие минимальным поведенческим тестом. Затем исправь основной и запасные пути. Не расширяй задачу соседним рефакторингом и гипотетическими улучшениями.
- Проверки не являются главным источником задержки, когда весь набор занимает секунды. Сохраняй значимые регрессионные тесты и обязательные проверки: затронутый набор после исправления, полный набор затронутого аддона один раз, синтаксис изменённых Lua-файлов и проверку пробелов в `jj diff --git`. Расширяй или повторяй проверки только после новых изменений, ошибок или появления нового риска.
- Запускай независимые финальные проверки параллельно. Возвращай только ошибки, итоговое число тестов и код завершения; не выводи сотни успешных строк и большой diff уже прочитанных изменений. Получай итог тестов в том же цикле проверки, сохраняя ненулевой код завершения при ошибке.
- После успешной проверки сразу дай короткий итог: причина, исправление, результат проверки, оставшаяся граница проверки в ESO. Не добавляй новый проход чтения кода только ради ссылок, пересказа или оформления ответа.
- Проси `/reloadui` только для необходимой проверки в клиенте. Объединяй нужные эксперименты в один установленный набор и одну команду; не требуй отдельной перезагрузки для каждого предположения.

## Граница проверки ESO

- Локальные Lua-тесты не воспроизводят автоматически приватность API, доверенность стека, серверную обработку и отрисовку ESO. Указывай, что проверено локально и что ещё требует клиента.
- Не читай и не вызывай приватный `RequestMoveItem` напрямую, в том числе через `type(api.RequestMoveItem)`. Используй публичный `CallSecureProtected` со строкой имени. Проверяй наличие публичного диспетчера; не добавляй прямой запасной вызов приватной функции.
- Регрессионный стенд для такой ошибки должен запрещать само чтение приватной функции. Успешный игровой эксперимент доказывает проверенный путь вызова; перенос в основной код требует проверки всех новых обращений и запасных путей.

## Сохранение поведения при локальных правках интерфейса

- Перед изменением сформулируй точный запрошенный результат и отдельно перечисли уже существующее поведение затронутого элемента: прокрутку, доступность пунктов, расположение, навигацию и работу при меньшем окне или масштабе интерфейса. Сохраняй эти свойства, если пользователь прямо не попросил изменить их или они не препятствуют запрошенному результату.
- Удаление строки списка не даёт разрешения удалять контейнер прокрутки или иное поведение списка. Не делай такой «сопутствующей уборки» по числу оставшихся строк. Высота панели зависит от разрешения, масштаба интерфейса и режима отображения.
- Не заменяй тест сохраняемого поведения проверкой, основанной на одном фиксированном размере панели. Для прокручиваемого списка оставь проверку контейнера и доступности последнего пункта; дополнительно проверь сценарий с меньшей высотой. Мок тестирует структуру и логику, а фактическую прокрутку и отрисовку подтверждай в клиенте ESO.
- Перед завершением просмотри удаления в diff: каждое удалённое поведение должно соответствовать явному пункту запроса или необходимому следствию исправления. Если связь нельзя объяснить конкретно, верни поведение и сузь изменение.

## Разбор задержек

- При вопросе о длительности используй временные метки журнала. Разделяй время инструментов, промежутки между действиями и пересборку контекста; не называй весь промежуток «тестированием» или «размышлением» без данных.
- Для короткого разбора используй хвост подтверждённого текущего журнала. Сначала проверь метаданные и последние даты. Не загружай многогигабайтную историю целиком и не анализируй старые сессии без необходимости.
